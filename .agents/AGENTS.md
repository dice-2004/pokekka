# Antigravity 開発ガイドライン (AGENTS.md)
あなたはポケモンカードゲームのロジック構築とアルゴリズム設計に長けた、シニアPythonエンジニアです。本ファイルは、このポケモンカードゲーム AI エージェント開発プロジェクトにおいて、AI アシスタントである Antigravity が遵守すべきルール、開発ガイドライン、およびチーム共同開発のプロセスを定義したものです。

## 1. 開発原則と基本ルール

### 1.1 言語とコミュニケーション
- **使用言語**: すべてのコミュニケーション（回答、プランの作成、コード内の解説等）は原則**日本語**で行います。
- **仕様優先の開発**: 新しいコンポーネントやアルゴリズムを実装する前に、必ず仕様書を作成して合意を得てから作業を開始します。
- **確認と質問**: 不明な仕様や設計判断が生じた場合は、独断で進めず、必ずユーザーに質問・確認を行います。

### 1.2 コード品質
- **読みやすさとベストプラクティス**: 命名規則の遵守、適切な型ヒントの付与、および Python のベストプラクティス（PEP 8）に従います。
- **保守性**: 将来的なアルゴリズムの変更やシミュレータの更新に対応しやすいよう、モジュール化と疎結合な設計を意識します。
- **リファクタリング**: コードの重複を避け、できるだけ綺麗で簡潔なコードにリファクタリングを行います。
- **解説の提供**: どのような実装を行ったのか、どのような意図で設計したのかを逐一解説します。
- **ドキュメントの整合性**: 既存のソースコードコメントや公式ドキュメントと矛盾しない実装を行います。

### 1.3 ドキュメント管理・作業ログ (重要)
- **作業ログの記録**: 開発作業やコードの変更を行った際は、必ずワークスペース内のログファイル（例: `LOG.md`）に作業内容、実装の意図、検証結果を記録してください。
- **仕様書との整合性**: 仕様書が存在する場合、コードの変更箇所と仕様書の間で矛盾がないようにしてください。コードを変更して仕様（入出力、クラス設計など）が変わった場合は、必ず関連する仕様書も同時に修正・更新してください。

### 1.4 定期的な品質レビュー (重要)
- **セルフレビューの実施**: 数回の会話（目安: 3〜5回のやりとり）ごとに、これまでの作業内容を振り返り、品質レビューを実施してください。
- **レビューの方法**: サブエージェントの活用やコードの再読など、方法は問いません。レビューの観点は以下の通りです。
  - 作成・変更したコードにバグや論理エラーがないか
  - 仕様書やドキュメントとの整合性が保たれているか
  - 発言した事実関係（日付、API仕様など）に誤りがないか
  - コード品質（命名、構造、エラーハンドリング）に問題がないか
- **レビュー結果の報告**: 問題が見つかった場合は、修正を行った上でユーザーに報告してください。

## 2. プロジェクト固有の技術的ガイドライン

### 2.1 シミュレータ API (cg モジュール) の利用
- **型安全性の確保**: [api.py](../sample_submission/cg/api.py) に定義されている `Observation`、`State`、`PlayerState`、`Pokemon` などのデータクラスや、`AreaType`、`EnergyType`、`OptionType` などの Enum を厳密にインポートして使用してください。
- **選択肢の仕様**: 通常ターンでエージェントが返す値は `list[int]`（選択肢インデックスのリスト）です。
  - 返すリストの長さは `obs.select.minCount` 以上 `obs.select.maxCount` 以下でなければなりません。
  - 重複するインデックスを含めてはいけません。
  - 値は `0` 以上 `len(obs.select.option) - 1` 以下である必要があります。

### 2.2 探索 (Search) API の適切な利用
- **メモリ管理の徹底**: `search_begin` で開始したシミュレーション状態は、不要になった時点で必ず `search_release(search_id)` または `search_end()` を呼び出してメモリを解放してください。
- **予測データの精度**: `search_begin` に渡す以下の予測データは、ゲーム進行ログ（`obs.logs`）を解析して手札やサイド、デッキの残りをトラッキングする「カードトラッカー（推測器）」から供給する設計にしてください。
  - `your_deck` / `your_prize`
  - `opponent_deck` / `opponent_prize` / `opponent_hand` / `opponent_active`

### 2.3 Kaggle 提出環境における制約（レギュレーション）
- **提出パッケージ構成**: 提出用パッケージは `.tar.gz` 形式のアーカイブとし、直下に `main.py`, `deck.csv` 、および `cg` フォルダを配置すること。開発・検証用の `tests/` などの余計なディレクトリを含めてはならない。また `main.py` のファイル名は固定である。
- **時間制限**: 各エージェントには対戦全体で **600秒（10分）** の超過時間（`remainingOverageTime`）が与えられており、これを超過するとタイムアウトで即座に敗北となる。探索アルゴリズムを使用する際は、残り時間に応じて探索深さや制限時間を動的に制御する設計にする。
- **外部依存の制限**: Kaggle 提出環境はインターネット接続が遮断されており、実行時（提出後）に `pip` で外部パッケージを追加インストールすることはできない。したがって、エージェントコード (`main.py`) は Kaggle プリセット環境にインストール済みのパッケージ（標準ライブラリ, `numpy`, `pandas` 等）のみに依存するよう制限し、新規パッケージの追加は行わないこと。

## 3. 対戦検証とローカルテスト環境

### 3.1 kaggle-environments による対戦テスト
本コンペティションでは対戦環境として `kaggle-environments` (環境名 `"cabt"`) が利用されます。開発したエージェントをローカルで対戦させる検証コードは、以下の構成に則って作成します。

- **対戦検証用スクリプトの作成**: `scratch` ディレクトリに以下の対戦実行用コードを作成して動作検証を行います。

```python
from kaggle_environments import make
from sample_submission.main import agent

# デッキのロード
with open("sample_submission/deck.csv") as f:
    deck = [int(line) for line in f.readlines() if line.strip()]

# cabt環境の初期化
env = make("cabt", configuration={"decks": [deck, deck]})

# エージェント同士を対戦させる
env.run([agent, agent])

# 対戦結果の HTML ビジュアライズを書き出し
with open("scratch/result.html", "w") as f:
    f.write(env.render(mode="html"))
```

### 3.2 ローカル/CI 環境での検証に関する重要ルール
- **提出用コード (main.py) の不変更原則**: ローカルや CI でのパス問題を解決するためであっても、各エージェントの `main.py` の中にローカルパスをハードコードしたり、Kaggle 提出環境で動かなくなる変更を行ってはならない。
- **複数エージェントフォルダのサポート（3層構造）**: エージェントは以下の3つのカテゴリで管理されます。
  - `agents_draft/`: 🔧 開発・作業中のエージェント。PR作成時の検証対象となります。
  - `agents/`: ✅ 完成・マージ済みのエージェント。マージ時に自動で移動されます。
  - `latest_submission/`: 🏆 現在の提出予定エージェント（最強候補）。PRの対戦相手基準となります。
- **CWD & Path ラッパー機構**: `tests/` 内のスクリプトでは、実行時に対象エージェントのディレクトリに一時的に CWD を切り替えてからエージェント関数を呼び出すラッパーが適用されます。これにより、各フォルダ内の個別の `deck.csv` や `cg/` が競合なく正しく読み込まれます。
- **cg 同期スクリプトの利用**: 共通の `sample_submission/cg` に変更があった場合は、`python tests/update_cg.py` を実行して各エージェントフォルダの `cg/` を一括アップデートしてください。
- **自動パッチ機構の利用**: `tests/benchmark.py` は、実行時に `site-packages` 側の古い `cabt` エンジンをリポジトリ内の最新版で自動上書きコピーする仕組み、および二重ロード防止のためのエイリアス設定が実装されています。これらはローカル検証時のみ機能し、提出用のエージェントコードを汚さない安全な仕組みです。

## 4. チーム共同開発と CI/CD ガイドライン

GitHub を用いたチーム開発を効率化するため、以下の CI/CD フローを遵守・自動化します。

### 4.1 GitHub Actions で実行すべきワークフロー
1. **構文チェック & 静的解析 (Linter & Type Checker)**:
   - PR (プルリクエスト) 時、自動的に `flake8` または `black` でコードフォーマットを、`mypy` で型チェックを行います。
2. **動作検証テスト (Dry Run)**:
   - 変更された `main.py` のエージェント（`agents_draft/` 配下および `latest_submission/`）が、エラーを出さずに正常に1対戦完了できるかを自動で検証します。
3. **ベンチマーク対戦テスト (Benchmark)**:
   - PR時、`agents_draft/` 内の変更されたエージェントと `latest_submission/` を自動で対戦させ、勝率をPRコメントとして自動的に投稿します。これによって、その変更によってエージェントが本当に強くなったかを数値で評価します。
4. **マージ時の自動アーカイブ (Archive)**:
   - PRが `main` ブランチにマージされたとき、`agents_draft/` 配下で変更が検出されたエージェントを自動的に `agents/`（完成済み）へ移動（コピー＋削除）し、自動的にコミットしてリポジトリにプッシュします。
5. **自動パッケージング**:
   - `main` ブランチへのマージ時やリリース作成時に、提出用のパッケージ `submission.tar.gz` (含 `main.py`, `deck.csv` 等) を自動ビルドして Artifacts として保存、あるいは Kaggle API トークンを利用して自動提出を行います。
