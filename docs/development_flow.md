# 開発の進め方・規約マニュアル (docs/development_flow.md)

本ドキュメントでは、本プロジェクトにおける開発フロー、コーディングおよび設計のルール、提出用パッケージの作成方法、およびブランチ戦略について解説します。

---

## 1. ブランチ戦略と命名規則

チーム開発での競合を防ぎ、CI/CD ワークフローを円滑に回すため、ブランチ作成時は以下のプレフィックス規約を厳守してください。

| ブランチプレフィックス | 用途 | 例 |
| :--- | :--- | :--- |
| `feature/` | 新機能の実装、新規エージェントの開発 | `feature/mcts-agent` |
| `fix/` | バグやエラーの修正 | `fix/memory-leak` |
| `hotfix/` | 緊急の修正（本番環境等での不具合） | `hotfix/timeout-fix` |
| `release/` | 提出前検証、リリース準備、パラメータ調整 | `release/v1.0-final` |
| `docs/` | ドキュメントの更新・追加 | `docs/update-readme` |
| `chore/` | CI/CD設定の変更、テストスクリプトの調整、その他雑務 | `chore/update-actions` |

## 2. エージェント管理フォルダ構造

エージェントコードは混乱を避けるため、以下の役割を持つフォルダ群で管理されます。主に開発者が使用する「3層エージェント構造」と、公式サンプルが配置される「サンプルデッキフォルダ」があります。

### エージェント管理構造

```text
├── agents_draft/   # 🔧 開発・作業中のエージェント (PR時の対戦対象)
├── agents/         # ✅ 完成・マージ済みのエージェント
└── latest_submission_path.txt # 🏆 現在の提出予定（最強候補）エージェントの相対パスを記述したファイル
```

1. **`agents_draft/` (作業用)**:
   - 新規開発や検証中のエージェントは、必ずこのディレクトリ配下に固有の名前のサブフォルダを作って作業を行います。
2. **`agents/` (完成アーカイブ)**:
   - PRが `main` ブランチにマージされた際、`agents_draft/` 配下の該当フォルダは Actions によって**自動的にこのフォルダへ移動（アーカイブ）**されます。開発者が直接このフォルダ内にファイルを新規作成・変更して PR を出すことはありません。
3. **`latest_submission_path.txt` (最強候補エージェントの指示)**:
   - リポジトリにおける現在の提出予定（最強候補）エージェントのフォルダ相対パス（例: `agents/StarEx`）を記述するテキストファイルです。
   - PRの対戦勝率ベンチマーク実行時、新しいエージェントはこのファイルに記載されているフォルダのエージェントと戦って強さを評価されます。
   - より強いエージェントが完成し、マージされた後は、このファイルの内容を新しいエージェントのパスに書き換えることで、最強候補を切り替えます。

### 公式サンプルフォルダ

```text
└── sample_deck/    # 🎁 ダウンロードされた公式サンプルエージェントフォルダ
```

- Kaggle公式サンプルエージェント（Lucario、Abomasnow等）が `tests/fetch_samples.py` を実行した際に自動ダウンロードされる配置先です。
- ダウンロードした公式サンプルをベースに開発を行いたい場合は、**手動でこのフォルダから `agents_draft/` へコピー**して作業を開始してください。

## 3. 開発の基本ステップ

新規にエージェントを開発する場合の標準的な流れは以下の通りです。

1. **開発ブランチの作成**:
   - `main` ブランチからブランチを切ります（例: `git checkout -b feature/mcts-agent`）。
2. **作業フォルダの作成**:
   - `sample_submission/` フォルダを丸ごとコピーし、`agents_draft/` 配下に配置します（例: `agents_draft/mcts_agent/`）。
3. **コードの実装**:
   - `agents_draft/mcts_agent/main.py` や `deck.csv` を変更・開発します。
4. **共通シミュレータ API (`cg` モジュール) の同期**:
   - 共通の `sample_submission/cg/` 内のモジュールが更新された場合は、以下を実行して開発中エージェントの `cg` ディレクトリを同期します。
     ```bash
     update_cg.sh
     ```
5. **ローカルでの動作検証とベンチマーク**:
   - ドライランによるエラーチェックや、`latest_submission` との対戦ベンチマークを実施して性能を測定します（※詳細は「[実行・テスト・検証マニュアル](testing_and_execution.md)」を参照）。
   - 実行前に、自動的に PR 時に動作するリンターと同等の静的チェックが走ります。
6. **ログの更新**:
   - コードの変更を行った際は、必ず **[log/](../log/)** ディレクトリ配下の適切な作業ログファイル（共通インフラの変更は `log/general.md`、各デッキの変更は `log/<デッキ名>.md`）の最上部に作業内容、実装の意図、検証結果を記録します。
7. **PRの作成とマージ**:
   - PR を作成し、CI がグリーンで勝率向上が確認されたらマージします。エージェントは自動的に `agents/` へアーカイブされます。

## 4. Git 操作に関する重要ルール

チーム開発における不整合を避けるため、リポジトリに変化を与えるすべての Git 操作は以下のルールに従って実行します。

### 4.1 AI アシスタントによる Git 操作の禁止
- コミット（`git commit`）、ブランチ作成（`git checkout -b`）、プッシュ（`git push`）、プル（`git pull`）などの操作は、**AI アシスタント側では行いません**。
- コードの修正が終わった後は、AI アシスタントはユーザーに作業完了を伝え、コミットやプッシュの実行をユーザー自身に依頼してください。

### 4.2 SSH 接続環境に依存する操作の回避策
- VS Code Dev Container 内から `git push` や `git pull` などの SSH 接続操作を実行する際、SSH Agent Forwarding の設定が不十分であると接続エラーが発生することがあります。
- このような場合は、**プッシュ・プル操作のみホスト側のターミナル（コンテナ外）から実行する** ことを推奨します。

## 5. Kaggle 提出用パッケージの作成方法

Kaggle にアップロードして提出するファイルは、必ず以下の構成で `.tar.gz` 形式に圧縮されている必要があります。

### 5.1 提出物の構成 (重要)
```text
submission.tar.gz/
├── main.py        # 提出用メインコード ( sample_submission/main.py からコピー )
├── deck.csv        # デッキ構成ファイル ( sample_submission/deck.csv からコピー )
└── cg/             # シミュレータ API ディレクトリ ( sample_submission/cg/ を丸ごとコピー )
```
- **注意**: `tests/` ディレクトリや `.github/` などの開発・テスト用ファイルは、提出アーカイブに**絶対に含めない**でください。
- また、`main.py` がネストされたフォルダ内に配置されていると、Kaggle上でモジュール読み込みエラーになります（解凍直後のルートに配置されている必要があります）。

### 4.2 手動圧縮コマンド
```bash
# 提出したいエージェントのディレクトリに移動します
cd sample_submission   # 例: agents_draft/my_agent 等

# ディレクトリ内で圧縮を実行し、プロジェクトルートへ保存します
tar -czvf ../submission.tar.gz main.py deck.csv cg/
```

## 5. 設計およびゲームエンジンの制約ルール

### 5.1 Kaggle 提出環境における時間制限 (600秒ルール)
- 各エージェントには、対戦全体で **600秒（10分）** の超過時間（`remainingOverageTime`）が与えられています。
- 1ターンごとの思考時間が極端に長かったり、探索アルゴリズムの深さが一定だったりすると、ゲーム後半で制限時間を超えてタイムアウト即座敗北となるリスクがあります。
- 探索アルゴリズム（MCTSなど）を使用する際は、残り時間に応じて探索の深さや制限時間を動的に縮小・制御するロジックを必ず組み込んでください。

### 5.2 外部パッケージ追加の禁止
- Kaggleの実行環境はインターネット接続が遮断されており、追加のライブラリ（`pip install` 等）を行うことはできません。
- したがって、エージェントコード (`main.py`) は Kaggle プリセット環境にインストール済みのパッケージ（標準ライブラリ, `numpy`, `pandas` 等）のみに依存するように制限して記述してください。

### 5.3 シミュレータ API (cg モジュール) の型安全性
- [cg/api.py](../sample_submission/cg/api.py) に定義されている `Observation`、`State`、`PlayerState` などのデータクラスや、`AreaType`、`EnergyType`、`OptionType` などの Enum をインポートして型安全に記述してください。
- 選択肢の仕様として、通常ターンにエージェントが返す値は `list[int]` (選択肢インデックスのリスト) です。
  - 返すリストの長さは `obs.select.minCount` 以上 `obs.select.maxCount` 以下でなければなりません。
  - リスト内に重複したインデックスを含めてはいけません。
  - インデックスの値は `0` 以上 `len(obs.select.option) - 1` 以下である必要があります。
